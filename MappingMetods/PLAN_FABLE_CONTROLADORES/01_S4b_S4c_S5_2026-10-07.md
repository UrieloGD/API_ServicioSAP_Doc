## 3. CQ3 explained (guests, idMagento 0-2) — still open

CQ3 in plain words.

**What it is about.** In Magento, a customer who buys without registering (a guest) has no real customer number. LAN used the numbers 0, 1 and 2 as a "guest" placeholder. Many guests share the number 0, so LAN never trusted the number alone for them: it looked for an account with number 0 AND the same email (SP_eCommerceCtenuevo.sql:62-68). For registered customers (3 and up) the number alone was enough; that is the CQ2 rule you just answered.

**The question.** When S5 adds "look before creating" to setCustomer, what should happen if a request arrives with idMagento 0, 1 or 2?

**Example.** Guest Ana (ana@x.com) and guest Luis (luis@x.com) both arrive with idMagento 0. If S5 searched SAP only for "ZidMagento = 0", Luis could get Ana's BP, or any BP that was never linked to Magento, because those carry ZidMagento 0 too. Today BPs created by order/new also carry 0: they store `info.idMagento` (OrderMethods.cs:2827), which is 0 with the current Magento payload (G04-29). That is why a guest search must include the email: "ZidMagento = 0 and Mail = ANA@X.COM".

**What the code shows.**
- No code we can read calls customer/setCustomer today: not Magento (app/code), not the PWA, not the DMZ itself. The only call in sap.log is your own Hoppscotch test.
- Guests are handled in order/new: with bank transfer they get the fixed guest BP 1500003857 (a DEV test BP); with other payment methods a new BP per order; with openpay_stores and credit they are rejected.
- So CQ3 is mostly a safety rule for a case we have not seen.

**Options.**
- **A1 (recommended):** treat it as "should not happen", but if id 0-2 arrives, apply the LAN rule: search by ZidMagento + email (uppercase, the way it is stored). Found: return that BP. Not found: create one. With the dynamic filter this is one extra condition.
- **A2:** if id 0-2 arrives, skip the search and create a new BP as today. Simplest, but the same guest email keeps creating duplicate BPs.
- **B:** same rule as A1, but treated as a normal case because Magento does send guests to setCustomer (you would confirm with the Magento/Omnipro owner).
- **C:** for id 0-2, return the fixed guest BP without calling SAP. The guest's name and email are then never stored, and 1500003857 is still a test BP until SAP provides the production one.

**How to answer.** Write "CQ3 = A1" (or A2, B, C). Until then S5 leaves id 0-2 exactly as today (create without searching), and it never searches by ZidMagento alone.

```csharp
private static string ArmarFiltroBp05(bool mayusculas, (string Campo, object Valor)[] condiciones)
{
    if (condiciones == null || condiciones.Length == 0)
        throw new ArgumentException("Filtro BP05 sin condiciones");
    var partes = new List<string>();
    foreach (var c in condiciones)
    {
        if (c.Campo == null || !CamposFiltroBp05.TryGetValue(c.Campo, out var tipo))
            throw new ArgumentException("Campo no permitido en el filtro BP05: " + c.Campo);
        string literal;
        if (tipo == typeof(int) && c.Valor is int entero)
            literal = entero.ToString(System.Globalization.CultureInfo.InvariantCulture);
        else if (tipo == typeof(string) && (c.Valor == null || c.Valor is string))
        {
            var texto = (string)c.Valor ?? string.Empty;
            if (mayusculas) texto = texto.Trim().ToUpperInvariant();
            literal = "'" + texto.Replace("'", "''") + "'";
        }
        else
            throw new ArgumentException("Valor de tipo incorrecto para el campo " + c.Campo);
        partes.Add(c.Campo + " eq " + literal);
    }
    return Uri.EscapeDataString(string.Join(" and ", partes));
}
```
New literals for approval: `Filtro BP05 sin condiciones`, `Campo no permitido en el filtro BP05: `, `Valor de tipo incorrecto para el campo `. They fire only on a programming or configuration error and leave through the caller's existing catch.

Why the encoded expression fits the existing URL: `GetFilterClientsAsync(string)` builds `...?$filter={sapFilter}&sap-client=110&$format=json` (BPM:221), and `System.Uri` keeps valid `%XX` sequences, which is how `FinalListProperMethods.cs:103` already sends its filter. public async Task<string> SetCustomerAsync(CustomerRequest customer)
{
    var sapClient = BuildClientFromCustomerRequest(customer);   // Sntz/Trim/UPPER e int.Parse como el alta (S4)
    var idMagento = sapClient.toCte.ZidMagento;

    if (idMagento > 2)   // SP_eCommerceCtenuevo.sql:62-68: con Id > 2 el idMagento identifica la cuenta
    {
        List<Partner> filas;
        try
        {
            filas = await GetFilterClientsAsync(false, ("ZidMagento", idMagento)).ConfigureAwait(false);
        }
        catch (Exception e) when (e.Message.Contains("No se encontraron clientes"))
        {
            filas = new List<Partner>();   // T1.1-03 (c): solo el no encontrado deja crear; cualquier otro error sube sin crear
        }
        var numeros = (filas ?? new List<Partner>())
            .Select(f => (f.BusinessPartner ?? string.Empty).Trim())
            .Where(n => n.Length > 0).Distinct().ToList();
        if (numeros.Count > 0)
            return numeros.OrderBy(n => n.Length).ThenBy(n => n, StringComparer.Ordinal).Last();   // CQ2 = a
        // CQ2: "si solo existe con IDmagento" (sin BP en SAP): se genera la cuenta, se crea abajo como hoy
    }
    // idMagento <= 2: pendiente CQ3; se crea como hoy, sin busqueda.

    var result = await SubmitClientInfoAsync(sapClient).ConfigureAwait(false);
    if (result == null || string.IsNullOrWhiteSpace(result.Partner))
    {
        var mensajes = result?.to_return?.results;
        var motivo = mensajes == null || mensajes.Count == 0
            ? "BP01 no devolvio un Partner valido"
            : (mensajes.FirstOrDefault(m => m.Type == "E") ?? mensajes[0]).Message;
        throw new Exception(motivo);   // controlador: Ok("Error, " + motivo), igual que hoy (CQ6 d + T1.1-12)
    }
    return result.Partner.Trim();
}
